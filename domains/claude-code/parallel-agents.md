## چه زمانی کار موازی؟

🧭 فقط وقتی کارها **واقعاً مستقل‌اند** (مثلاً صفحه‌ی «درباره‌ی ما» و فرم تماس). کارهای به‌هم‌وابسته را موازی نکن؛ وقت ادغام و حل تعارض بیشتر از وقت صرفه‌جویی‌شده می‌شود. هر جلسه یا زیرعامل موازی **درخواست‌های خودش را جدا هزینه می‌کند** ([هزینه و کارایی](cost-efficiency.md)).

## ابزارها

| ابزار | چه می‌کند | وضعیت |
|---|---|---|
| **`claude --worktree <name>`** (یا `-w`) | جلسه را در یک worktree جدای git باز می‌کند: پوشه‌ی `.claude/worktrees/<name>/` روی شاخه‌ی تازه‌ی `worktree-<name>` | ✅ |
| **`isolation: worktree`** در frontmatter زیرعامل (`.claude/agents/*.md`) | هر بار که آن زیرعامل اجرا شود، worktree خودش را می‌گیرد؛ اگر تغییری نداد، worktree خودکار پاک می‌شود | ✅ |
| **`.worktreeinclude`** در ریشه‌ی پروژه | فایل‌های gitignore‌شده (مثل `.env`) را به هر worktree تازه کپی می‌کند؛ با نحو `.gitignore`؛ **فقط فایل‌هایی که هم با الگو جورند و هم gitignore شده‌اند** | ✅ |
| **جلسه‌ی پس‌زمینه** | `claude --bg "<prompt>"`، یا `/bg` برای جلسه‌ی فعلی؛ `/fork` برای کپی جلسه؛ `claude agents` برای نمای همه (پیش‌نمایش پژوهشی) | ✅ |
| **زیرعامل پس‌زمینه** | فیلد `background` در frontmatter | ✅ |
| **`/batch <instruction>`** | یک تغییر بزرگ را بین ۵ تا ۳۰ زیرعامل تقسیم می‌کند، هر کدام در worktree خودش | ✅ |
| **تیم عامل‌ها** | چند هم‌تیمی با پنجره‌ی context جدا؛ آزمایشی، با `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`؛ پیشنهاد رسمی **۳ تا ۵ هم‌تیمی**؛ در حالت plan حدود ۷ برابر توکن | ✅ |
| **چند جلسه در اپ دسکتاپ** | هر جلسه اختیاری در worktree خودش | ✅ |

مستندات: https://code.claude.com/docs/en/worktrees · https://code.claude.com/docs/en/agent-teams · https://code.claude.com/docs/en/agent-view

## محافظت worktree: دقیقاً چه چیزی را جلو می‌گیرد؟

✅ (بخش «How Claude Code enforces isolation») وقتی Claude در یک worktree کار می‌کند:
- ویرایش فایل (Edit، Write) که **به پوشه‌ی اصلی پروژه** اشاره کند، رد می‌شود
- دستور شل که پوشه‌ی کاری‌اش پوشه‌ی اصلی باشد، رد می‌شود
- هدایت git به پوشه‌ی اصلی (`git -C`، `--git-dir`، `GIT_DIR`، `GIT_WORK_TREE`، یا `cd` قبل از git) رد می‌شود
- دستوری که قابل بررسی نباشد، رد می‌شود (این بررسی خاموش نمی‌شود)

⚠️ **اما:** طبق همان صفحه، نوشتن با شل بدون git (مثل `cp` یا هدایت خروجی `>` به پوشه‌ی اصلی) **با این بررسی‌ها رد نمی‌شود**. پست منبع گفته بود «هر ویرایش بیرون از worktree مسدود است»؛ دقیق نیست.

## الگوی پیشنهادی ما

🧭 (الگوی «نویسنده و بازبین» در مستندات بهترین روش‌ها، به‌علاوه‌ی worktree)
1. جلسه‌ی اصلی: برنامه‌ریزی و تقسیم کار به قطعه‌های مستقل
2. هر قطعه در worktree خودش (جلسه‌ی جدا یا زیرعامل با `isolation: worktree`)
3. هر قطعه با معیار پایان روشن ([بررسی خودکار](verification.md))
4. جلسه‌ی اصلی یا یک جلسه‌ی تازه بازبینی و ادغام می‌کند

❓ پست منبع گفته بود «Anthropic همین الان این را منتشر کرد» و «Sonnet جلسه‌ی اصلی را اجرا کند». هیچ‌کدام در مستندات رسمی نیست؛ تنها توصیه‌ی Sonnet در مستندات برای **هم‌تیمی‌ها** در تیم عامل‌هاست.

⚠️ `.worktreeinclude` فایل‌های `.env` را در هر worktree کپی می‌کند؛ یعنی رمزها در چند جا پخش می‌شوند. فقط فایل‌های لازم را فهرست کن.

🔬 **`node_modules` در worktree:** لینک نمادین `ui/node_modules` به `node_modules` پوشه‌ی اصلی برای `tsc --noEmit` کار می‌کند، ولی `next build` با Turbopack رد می‌شود (خطای «Symlink [project]/node_modules is invalid, it points out of the filesystem root»). راه: در worktree فقط بررسی نوع بگیر و ساخت نهایی را پس از ادغام در پوشه‌ی اصلی انجام بده، یا در خود worktree `npm ci` بزن.

```text
Split this work into independent pieces that touch different files: [task list]. For each
piece, use a subagent with worktree isolation, give it a clear done-condition it can check
itself (a test, a build, or a screenshot), and do not let two pieces edit the same file.
When all pieces finish, review each diff, then merge them one at a time and run the full
checks after each merge.
```

⛔ پست منبع Jev را هم برای «تصمیم‌های سریع» در همین الگو تبلیغ کرده بود: [کارت jev-guard](../../catalog/jev-guard.md).

## کار موازی بدون git

✅ مستندات رسمی ([S68](../../sources/README.md#s68)):
- worktree **مخزن git لازم دارد**؛ برای سیستم دیگر باید hookهای `WorktreeCreate` و `WorktreeRemove` بنویسی.
- checkpoint و `/rewind` **تغییرهایی را که با دستور Bash انجام شده ردیابی نمی‌کنند** (`rm`، `mv`، `cp`).
- ویرایش زیرعامل‌ها معمولاً با `/rewind` جلسه‌ی اصلی برنمی‌گردد؛ مستندات برای برگرداندنشان git را پیشنهاد می‌کند.

پس در پوشه‌ای بدون git، زیرعامل‌های موازی **هیچ جداسازی و هیچ برگشت خودکاری** ندارند. الگوی ما:

1. 🔬 **مالکیت سخت فایل:** هر فایل فقط یک صاحب دارد؛ دو زیرعامل هرگز یک فایل را ویرایش نمی‌کنند.
2. 🔬 **فایل‌های مشترک** (طرح پایگاه داده، برچسب‌ها، فایل‌های ترجمه) را فقط جلسه‌ی اصلی ویرایش می‌کند.
3. 🔬 هر زیرعامل در گزارشش فهرست **«از اصلی لازم است»** می‌دهد (مثلاً «یک ستون تازه در طرح»، «این برچسب در سه زبان»)؛ جلسه‌ی اصلی در پایان همه را یک‌جا اعمال می‌کند.
4. 🧭 **پیش از شروع، یک عکس فوری** با `tar` از پوشه بگیر (بدون `node_modules` و داده‌ی بزرگ) و **بعد از پایان** با `diff -r` مقایسه کن تا ببینی دقیقاً چه فایل‌هایی عوض شد و چیزی بیرون از سهم هر صاحب تغییر نکرده.
5. 🧭 بعد، کل تست‌ها یک بار.

🔬 در یک پروژه‌ی واقعی که مخزن git ندارد، این الگو بارها به کار رفت، از جمله در رفع حدود ۶۰ یافته‌ی [بازبینی انتقادی](verification.md#بازبینی-انتقادی-پنجبعدی-با-بازبینهای-موازی). درس ثبت‌شده‌ی پروژه: «با مالکیت سخت فایل خوب کار کرد».

⚠️ 🧭 اگر می‌توانی، **اول `git init` کن**؛ همه‌ی این‌ها با worktree و git ساده‌تر و امن‌تر است. این الگو برای وقتی است که نمی‌شود (مثلاً صاحب پروژه git نمی‌خواهد).

```text
This folder has no git, so split the work by file ownership. Before starting, make a tar
snapshot of the source (excluding node_modules, data and build output). Give each
subagent a list of files it alone may edit; shared files (schema, labels, translations)
stay with you. Each subagent reports what it changed and a "needed from main" list. When
all finish, apply the shared changes yourself, diff the folder against the snapshot to
confirm nobody edited outside their files, then run the full test suite.
```

## چند عامل روی یک بک‌اند و یک پنل زنده 🔬

از یک پنل ادمین واقعی (۲۰۲۶-۱۰-۲۲، ۱۰ عامل): هر عامل یک بخش (صفحه + ماژول بک‌اند + آزمون) با مالکیت سخت فایل؛ فایل‌های مشترک (پیکربندی ماژول‌ها، middleware، جدول کارهای تأیید) فقط با «ویرایش یک‌خطی» زیر یک خط علامت‌دار؛ git فقط دست هماهنگ‌کننده که هر بخش را بعد از گزارش با مسیرهای صریح commit کرد.
- 🔬 **سرور dev مشترک با هر ذخیره‌ی هر عامل دوباره راه می‌افتد** و آزمون‌های بقیه را با «fetch failed» یا ECONNREFUSED می‌شکند: در دستور عامل‌ها «تا ۲ دقیقه صبر و دوباره» بنویس و آزمون پایانی یک‌جا را بعد از تمام شدن همه اجرا کن.
- 🔬 **سقف‌های امنیتی واقعی بین آزمون‌ها مشترک می‌شوند:** محدودیت «۳۰ درخواست passkey در ۱۰ دقیقه برای هر IP» (همه از localhost) و «حداکثر ۱۰ passkey برای هر حساب» (هر ورود آزمایشی یکی می‌ساخت) ورود همه‌ی عامل‌ها را خواباند. راه: هر مرورگر آزمون `X-Forwarded-For` جدا، پاک کردن passkey خود آزمون در پایان (`close(ctx)`)، و تغییر زبان فقط برای همان نشست آزمون.
- 🔬 **یک عامل بسیار طولانی دو بار از کار افتاد** (بی‌پیشرفت ۱۰ دقیقه، بعد «Unknown error»). ادامه دادنش کار نکرد؛ عامل تازه با فهرست فایل‌های ساخته‌شده و دستور «اول بخوان و قضاوت کن، از نو نساز» کار را در نیم ساعت تمام کرد.
- 🔬 **گذر یکپارچه‌سازی جدا لازم است:** هر عامل فهرست «تغییر لازم در فایل‌های مشترک» داد (تنظیمی که ذخیره می‌شد ولی کسی نمی‌خواند، کف قیمت در دو جا، نام عربی که سایت نشان نمی‌داد، دو رویداد هم‌معنی). یک عامل آخر همه را با آزمون بست و همه‌ی آزمون‌ها را در یک دستور گذاشت.
- 🔬 `systemd-run --user` مسیر PATH نشست را نمی‌گیرد و Node سیستم (۲۰) را اجرا کرد؛ با `systemd-run ... /usr/bin/env PATH=$PATH node ...` همان Node پروژه اجرا می‌شود.

## دو سازنده با مالکیت سخت فایل 🔬
در یک فاز Next.js (۲۰۲۶-۱۰-۳۰) دو زیرعامل Opus در یک worktree ساختند (حدود ۳۰۰ هزار توکن و ۱۵ دقیقه برای هر کدام) و آزمون‌ها سبز شد:
- **جدول‌های مشترک را جلسه‌ی اصلی پیشاپیش اضافه کند** تا هیچ سازنده‌ای به schema دست نزند.
- **هر سازنده فقط فایل‌های خودش را عوض کند** و تغییر فایل‌های مشترک را در یک فایل تحویل با متن دقیق قبل و بعد بنویسد.
- **جلسه‌ی اصلی تحویل‌ها را با اسکریپت اعمال کند** و بسنجد متن قدیمی دقیقاً یک بار پیدا شود.
- **دام:** import که «بعد از خط اول» گذاشته شد داخل توضیح `/**` افتاد؛ بعد از اولین import واقعی بگذار.
- آزمون‌های وابسته به داده‌ی seed را روی داده‌ی تازه اجرا کن.
- 🔬 در دور بعد با قرارداد ثابت خروجی‌ها در بریف، ۲۵ تغییر تحویلی بار اول اعمال شد و هیچ جای خالی لازم نشد (۲۴ دقیقه برای هر سازنده، جمعاً حدود ۷۰۰ هزار توکن).

## چرا عامل‌ها اشتباه می‌کنند و چطور جلویش را بگیریم 🔬

از یک پروژه‌ی واقعی ([S76](../../sources/README.md#s76)) ثبت شد. هر ردیف: علت، نشانه، پیشگیری.
- 🔬 **یک واقعیت در چند جا تایپ می‌شود.** عامل‌های مختلف در زمان‌های مختلف همان عدد را نوشتند و عددها لغزیدند: سایت تعداد معامله را ۲۱۷ و ۲۱۸ و ۲۱۶ و ۱۵۲ و «۲۰۰+» نشان داد، در حالی که عدد واقعی ۲۱۷ بود (بسته‌ها به‌مرور بزرگ شده بودند). پیشگیری: برای هر واقعیت یک منبع حقیقت؛ صفحه‌ها عدد را از داده **محاسبه** کنند (مثلاً یک فایل آمار)، نه تایپ؛ در build سایتِ ساخته‌شده برای هر عدد شناخته‌شده گشته شود و با ناهمخوانی شکست بخورد؛ عامل باید برای هر عددی که می‌نویسد فایل منبعش را نام ببرد.
- 🔬 **تصمیم محلی با زمینه‌ی ناقص.** یک عامل خودسرانه نسخه‌ی اپ را به 1.3.0.0 برد و عامل دیگر تستی نوشت که به همان نسخه میخ شده بود؛ یک POST ناقص تنظیمات فیلدهای دیگر را به پیش‌فرض برگرداند؛ دو رفع‌کننده یک فایل بزرگ را هم‌زمان ویرایش کردند. پیشگیری: در دستور کار بنویس چه کسی مالک کدام فایل/تنظیم است، «نسخه را تغییر نده»، «همیشه شیء کامل بفرست»؛ برای نوشتن مشترک قفل (مثلاً `flock` برای strings.json)؛ یک **یکپارچه‌ساز** که تنها او commit می‌کند؛ برای هر تغییر یک ردیف در گزارش تغییرها.
- 🔬 **«تمام شد» از دید خود عامل.** هماهنگ‌کننده آن را بی‌بررسی بازگو می‌کند. پیشگیری: خودت diff و نتیجه را ببین، بازبینی مخالف‌خوان، و پیش‌انتشار را هرگز پیش از آزمون صاحب پروژه روی ماشین خودش منتشر نکن.
- 🔬 **از دست رفتن زمینه در نشست‌های طولانی و فشرده‌سازی** خطاهای تکراری می‌سازد. پیشگیری: `STATE.md` و گزارش تغییرها را اول بخوان؛ قاعده‌های صاحب پروژه در یادداشت حافظه.
- مدل هر جا واقعیتی نداشته باشد می‌سازد یا گرد می‌کند: [بررسی خودکار](verification.md).

## حافظه: چرا Claude دسکتاپ یک‌باره بسته می‌شود

> ⭐ قانون کامل و ابزار خودکار: [قانون منابع](resource-safety.md) (۲۰۲۶-۱۰-۲۴). ⚠️ `MemoryHigh` را همراه `MemorySwapMax` نگذار؛ کار را گیر می‌اندازد.

✅ (لاگ یک رایانه‌ی لینوکسی، ۲۰۲۶-۱۰-۱۹؛ [S102](../../sources/README.md#s102)) روی لینوکس، اپ Claude دسکتاپ و **همه‌ی جلسه‌های Claude Code و هر دستوری که اجرا می‌کنند** (build، تست، مرورگر بدون رابط، زیرعامل‌ها) داخل یک «scope» در systemd هستند. وقتی حافظه‌ی کل سیستم پر شد، OOM killer کل همان scope را کشت و اپ بسته شد:
- ساعت ۰۱:۵۱: اوج **۲۷.۶ گیگابایت** حافظه و ۱۸.۷ گیگابایت swap برای scope اپ؛ «Failed with result 'oom-kill'».
- ساعت ۰۲:۲۲: دوباره، اوج ۲۵.۴ گیگابایت.
- خود اپ (Electron) فقط حدود ۱ گیگابایت بود؛ بقیه مال فرزندها بود (۷۸ پروسه‌ی فرزند در لحظه‌ی فشار) از جلسه‌های هم‌زمان چند پروژه.
- بیرون از اپ هم Ollama (حدود ۳.۷ گیگابایت) و پایگاه داده و سرویس‌های پروژه‌های دیگر حافظه می‌گرفتند.

🧭 نکته‌ها:
- **`/tmp` روی سیستم آزموده‌شده tmpfs است** (حافظه‌ی رم، سقف ۱۶ گیگابایت). هر فایلی که دستورها در `/tmp` می‌نویسند (build، بسته‌ی release، داده‌ی تست) از رم کم می‌کند و جزو حافظه‌ی همان scope حساب می‌شود.
- کار سنگین (تست بزرگ، build، ساخت release با مدل) را با سقف حافظه‌ی جدا اجرا کن تا فقط همان کشته شود، نه کل اپ. ⚠️ **`MemoryMax` به‌تنهایی کافی نیست:** ✅ `MemorySwapMax` سقف جداگانه‌ی swap است و پیش‌فرضش بی‌سقف است (`man systemd.resource-control`، [S107](../../sources/README.md#s107)). 🔬 (یک پروژه‌ی سفارش با QR، ۲۰۲۶-۱۰-۱۹) برنامه‌ای که ۵۰۰ مگابایت می‌گیرد زیر `MemoryMax=100M` کشته **نشد**: ۱۰۰ مگابایت در رم و ۳۹۲ مگابایت در swap، و تمام شد؛ با `--scope` هم همین. رایانه‌ی آزمون حدود ۳۲ گیگابایت swap دارد (NVMe + zram)؛ پس دستور قبلی جلوی همان بسته شدن را نمی‌گرفت. فقط با `MemorySwapMax` کشته شد:
  ```bash
  systemd-run --user --wait --pipe --same-dir -p MemoryMax=8G -p MemorySwapMax=512M -- <command>
  ```
  🔬 `--wait --pipe` (به‌جای `--scope`) در پایان «Memory peak» و «Finished with result: oom-kill» را چاپ می‌کند؛ شاهد خوب برای هر اجرا. کد خروج کار را نگه می‌دارد. متغیرهای محیط را با `-E PATH="$PATH"` بده (مثلاً Node از nvm). نمونه‌ی کامل: `check-all.sh` در یک پروژه‌ی سفارش با QR (همه‌ی بررسی‌ها، اوج ۰٫۷ تا ۱ گیگابایت، سقف ۲ گیگابایت).
- چند جلسه‌ی سنگین را هم‌زمان نگه ندار (مثلاً گردش‌کار چندصدعاملی کنار تست‌های بزرگ پروژه‌ی دیگر).
- مدل محلی (Ollama) را وقتی لازم نیست خاموش کن.
- خروجی بزرگ را به‌جای `/tmp` روی دیسک بنویس.
